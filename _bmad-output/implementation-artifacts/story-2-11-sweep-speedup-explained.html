Making the sweep faster without changing any result

Optional follow-up (a possible Story 2.11) after Story 2.10. All times are rough estimates from the measured run (window_len 20, r1, svm: extraction 365 s, head 20 s). Nothing here has been built yet.

Rule for both ideas: every run must produce the same numbers as today. Only who computes what, and when changes. Section 4 says how that is checked.

1. What happens today

csi-bench sweep runs the 216 runs one after another in one process. Each run does: load, preprocess, extract features (from cache if it exists), then fit the head. The feature cache is keyed per extractor, window length and room set. Two things are wasteful:

  • Same work, repeated. paper_beamforming is computed 12 times (4 window lengths × 3 room sets). Its slow part, the per-position metrics, does not depend on window length and not on which rooms you pick, yet it is recomputed each time.
  • Idle CPU. The machine has 16 threads. svm uses one core, and only one run is active at a time, so most cores wait.

2. Idea A: compute the per-packet metrics once and reuse them

Story 2.10 already computes, for every packet position in a block, six numbers (doppler, distance, flatness). Each number depends only on the packets at that position. A window just takes a slice of them and runs var / mean.

So the per-position arrays do not depend on window_len, and r1+r2 is the union of the r1 and r2 blocks. Store these arrays once in the runner-owned cache, keyed by recording block, fix_distance_loop and extractor VERSION. Each run then only slices (seconds).

What changes in code: a second runner-owned cache entry for the per-position arrays, and an extractor method that accepts them. The current extract_blocks becomes "get arrays, then slice". The final feature matrix and its cache key stay the same.

3. Idea B: run several sweep processes at once

Runs are independent: each has its own config, seeds and run directory. So several worker processes can take runs from the same sweep file. What must be added is coordination, not new maths:

  • a claim lock per run directory (atomic file create) so two workers never take the same run;
  • a lock per feature-cache key so only one worker computes a missing matrix and the others wait for it (this is why do A first);
  • safe updates of the sweep index / report inputs.

Memory: about 1.3–1.5 GB per worker, so 3–4 workers fit in 11 GB. The knn and random-forest heads already use several cores, so they gain less than svm.

4. Why the results cannot change

  • Idea A: the per-position arrays are the same numbers that are computed today, just stored once. Same check as in Story 2.10: the new feature matrix must equal the cached old one bit-for-bit, and an exact-equality test runs old path vs new path (both fix_distance_loop values, several window lengths, r1+r2). If it is not equal, the idea is dropped or a human decides.
  • Idea B: a run depends only on its own config and seeds, never on the order or on other runs. Check: run a small sweep serially and with 3 workers, then compare every metrics.json and predictions.parquet for equality. Run ids and cache keys do not change.
  • Not used: larger stride, float32 maths, smaller grids, other SVM libraries. Those would change the numbers.
